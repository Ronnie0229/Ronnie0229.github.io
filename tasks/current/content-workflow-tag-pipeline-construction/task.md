# RonnieCross Content Workflow Tag Pipeline Construction

## 1. 任务性质

本任务是新的、完全独立的建设任务，负责为 RonnieCross 个人网页项目建设统一的内容发布标签流水线（Tag Pipeline）。

本任务不是日常文章整理或发布任务，不是历史文章标签迁移任务，不是 GEO Knowledge Layer 改造任务，也不是 AI 自动标签接入任务。

任务完成后必须停止，等待独立复审；未获用户明确授权不得 push，不得进行生产发布。

---

## 2. 背景与问题定义

当前内容发布入口的标签处理仍未完全统一：

- 分享文章导入已要求人工提供精准 SEO 标签，并具有书卷补充、去重、数量限制和通用标签拦截能力；
- Admin 页面已具备书卷补充、2–6 个标签限制、通用标签拦截和人工标签输入；
- 教会讲道导入器仍会先写入旧式默认标签，例如 `讲道`、`教会讲道`、讲员姓名，随后依赖人工修改；
- 不同入口存在重复或分散的标签生成与校验逻辑；
- 后续若新增批量导入、API、移动端或自动同步入口，可能再次绕过现有规则。

因此，本任务不得只修补某一个导入器，必须建设独立、统一、可测试、可扩展的 Tag Pipeline，并使所有发布入口通过同一套接口生成和校验标签。

---

## 3. 正式目标

### 3.1 建立独立 Tag Pipeline 模块

建设一个与具体发布入口解耦的统一标签模块，作为整个网站唯一允许的标签生成、规范化与校验入口。

所有现有和未来发布入口必须调用该模块，包括但不限于：

- 分享文章导入；
- 教会讲道导入；
- `content_workflow.py` 的其它 publish 子命令；
- Admin 页面发布与保存；
- 后续批量导入；
- 后续 API；
- 后续移动端；
- 后续自动同步；
- 后续 AI Tag Provider。

任何发布入口不得自行拼装、默认写入或绕过校验后直接写入 `tags`。

### 3.2 建立三层标签模型

#### 第一层：确定性标签

从明确结构化字段生成：

- 根据 `scripture` 识别圣经书卷；
- 自动加入标准书卷标签；
- 多段经文应正确识别多个书卷，但最终标签总数仍受 2–6 个约束；
- 不得将 category、内容类型或讲员姓名自动当作 SEO 主题标签。

#### 第二层：规则推断标签

基于已批准且可验证的规则，从以下字段推断标准主题标签：

- `title`；
- `subtitle`（若存在）；
- `scripture`；
- `category`（只用于规则上下文，不得直接作为通用标签）；
- `speaker` / `author`（只用于上下文，不得默认直接成为主题标签）；
- 可维护的标签字典和标题匹配规则。

规则推断目标包括：

- 圣经人物；
- 地点；
- 事件；
- 明确主题。

规则必须确定、可测试、可解释。不得在本阶段使用 AI、模糊模型推断或外部服务。

#### 第三层：人工补充标签

保留并统一支持：

- CLI `--tags`；
- Admin 标签输入框；
- 其它未来入口传入的人工候选标签。

人工标签可以追加，但必须经过同一 Tag Pipeline 的规范化、别名映射、去重、通用标签拒绝和数量校验。

### 3.3 建立统一 Tag Validator

统一实现并供所有入口复用：

- 清理首尾空白；
- 拒绝空标签；
- 标签去重；
- 别名规范化后再次去重；
- 最终标签数必须为 2–6 个；
- 拒绝 generic tags；
- 拒绝仅由分类、内容类型或作者构成的标签集合；
- 标签字符与长度合法性检查；
- 对非法输入 fail closed，不得静默降级为旧式通用标签；
- 返回可供 CLI 和 Admin 使用的明确错误信息。

初始 generic tag 集合至少覆盖当前已经明确禁止或无检索价值的词：

- 分享；
- 灵命成长；
- 讲道；
- 教会讲道；
- 文章；
- 查经；
- 生命反思；
- 信仰；
- 基督教。

是否扩充该集合必须依据现有规范和测试，不得任意扩大。

### 3.4 建立 Tag Dictionary

建设可维护的标签字典，至少支持：

- 标准标签名；
- 中文别名；
- 英文别名；
- 同义词统一；
- 常见人物名和书卷名映射；
- 未来扩展字段的稳定结构。

示例目标：

- `Jacob`、`以色列（人物语境）` → `雅各`；
- `Abraham`、`Abram`、`亚伯兰` → `亚伯拉罕`；
- `Noah` → `挪亚`；
- `Cain` → `该隐`；
- `Paul`、`使徒保罗` → `保罗`。

必须避免把具有语境歧义的词在所有场景下无条件映射。例如“以色列”可能指雅各本人、民族或国家，规则应 fail closed 或只在明确语境下映射。

## 4. 已批准的追加架构建议

### 4.1 Tag Pipeline 必须是独立模块

不得仅在 `import_sermons.py`、`import_shares.py` 或 Admin 中复制相似逻辑。必须形成一个明确的共享模块或共享合同，使 Python 发布脚本和浏览器端 Admin 能够使用同一规则来源。

若 Python 与浏览器 JavaScript 无法直接调用同一运行时代码，必须设计单一权威规则源，例如机器可读配置或生成产物，并证明两端不会漂移。

### 4.2 新发布入口治理规则

以后任何新增发布入口，包括批量导入、API、移动端、自动同步或 AI 建议标签，必须先接入 Tag Pipeline。

未经 Tag Pipeline 校验，不得写入 Front Matter。

这是一项长期架构约束，不是当前实现的临时约定。

### 4.3 先完成架构设计再编码

建设会话必须先只读审查现有实现和规范，完成 Tag Pipeline 的模块边界、数据流、接口合同、权威规则源与迁移方案设计，并写入 `tag-pipeline-design.md`。

设计应在同一建设会话中完成并据此实施，但不得跳过设计直接在各入口打补丁。

若审查发现现有架构无法在本任务边界内安全统一，应记录阻断和建议，不得以复制逻辑掩盖问题。

- 新增机器可读标签字典或规则配置；
- 新增测试、fixture 和验证脚本；
- 与标签规则直接相关的 SEO、内容发布和 Admin 使用文档；
- 本任务目录中的设计、进度、验证与交接文档。

可根据实际依赖调整具体文件，但不得借此扩大到文章正文、Knowledge Layer 或其它无关系统。

## 6. 明确禁止事项

本任务不得：

- 修改任何历史文章正文；
- 批量改写历史文章 tags；
- 以迁移旧数据为理由改动现有已发布文章；
- 修改历史审计记录、历史裁决或已有发布证据；
- 修改 GEO Knowledge Layer 的主题提取、JSON-LD、canonical、sitemap、RSS 或相关文章逻辑；
- 接入 OpenAI、Hermes、Qwen、Gemma 或任何 AI Provider；
- 使用模型自动理解全文并生成标签；
- 引入外部网络依赖；
- 进行真实文章生产发布；
- 操作 NAS 收件、归档或挂载；
- 修改与标签系统无关的功能；
- 为使测试通过而削弱现有 SEO 标签规则；
- 静默接受非法标签并退回 `讲道`、`教会讲道`、讲员姓名等旧式默认值；
- 未获用户明确授权 push。

允许在本地提交建设结果，但是否 commit 应遵循工作区现有治理规则和用户授权；无论是否 commit，均不得 push。

## 7. 必须完成的测试

至少覆盖以下测试类别：

### 7.1 分享文章

- scripture 自动补书卷；
- 人工标签追加；
- 2–6 个最终标签；
- 通用标签拒绝；
- 与现有分享发布行为兼容。

### 7.2 教会讲道

- 不再默认输出 `讲道`、`教会讲道`、讲员姓名；
- 从 scripture 和标题得到可解释的标准标签；
- 无足够精准标签时 fail closed，并要求人工补充；
- 多段经文处理正确。

### 7.3 Admin

- 自动补入书卷；
- 手动输入标签保留；
- 通用标签拒绝；
- 数量限制；
- 错误提示明确；
- 保存与发布使用同一规则。

### 7.4 Validator 与 Dictionary

- Generic Tag Test；
- Duplicate Tag Test；
- Alias Test；
- 中英文别名测试；
- 空值与非法字符测试；
- 规范化后二次重复测试；
- 数量上下界测试；
- 语境歧义 fail-closed 测试。

### 7.5 Rule Generation

至少使用固定 fixture 覆盖：

- `信仰的殿堂：雅各`；
- `没有道路时的信心` 与亚伯拉罕相关输入；
- 挪亚相关讲道；
- 分享文章人物、地点和主题输入；
- 只有通用分类信息、无法推断主题的输入。

### 7.6 回归验证

必须运行并记录：

- 新增 Tag Pipeline 单元测试；
- 现有 Admin 保存检查；
- 现有 Knowledge Layer 检查；
- 整站构建；
- 与本次改动直接相关的现有内容工作流测试。

不得通过修改历史文章来消除回归失败。

## 8. 验收标准

只有同时满足以下条件，才可宣告建设完成：

1. 所有现有发布入口使用统一 Tag Pipeline 或同一权威规则源；
2. 教会讲道导入不再生成旧式通用标签；
3. 分享导入和 Admin 不发生规则退化；
4. 最终标签稳定限制在 2–6 个；
5. generic tags 和别名规则由单一权威来源管理；
6. Python 与 Admin 规则一致性有自动测试或生成校验保障；
7. 无法生成足够精准标签时 fail closed；
8. 全部规定测试通过；
9. Knowledge Layer 检查 0 错误、0 警告；
10. 整站构建成功；
11. 未修改历史文章正文或批量历史标签；
12. 未接入 AI Provider；
13. 未进行生产发布；
14. 未 push。
