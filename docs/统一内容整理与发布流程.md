# 统一内容整理与发布流程

本项目统一处理“分享”和“讲道”两类资料。Codex 的日常内容入口使用“整理并发布分享或讲道资料”对话，正式工作目录必须是本机 SSD 上的 Git 仓库。

## 初次准备

```shell
python -m pip install -r requirements.txt
npm install
```

Windows 和 macOS 都使用 `python`、`npm` 命令，不使用 `npm.cmd` 或硬编码的 Git 路径。

收件目录和归档目录通过环境变量提供：

- `RONNIE_SHARE_INBOX`：分享收件目录
- `RONNIE_SERMON_INBOX`：讲道收件目录
- `RONNIE_SERMON_ARCHIVE`：教会讲道受保护归档目录

Mac 端如果 `python` 不存在，使用 `python3`；若首次发布时报 `ModuleNotFoundError: No module named 'pypdf'` 或 `python-docx` 相关错误，应先执行：

```shell
python3 -m pip install -r requirements.txt
```

这属于本机依赖初始化，不代表内容发布失败。依赖安装后必须重新执行 dry-run，不得跳过 dry-run。

## 跨项目文档同步规则

讲道整理项目与个人网页项目共同维护讲道发布流程。以后只要新增或修改讲道整理、讲道翻译、讲道发布、NAS 归档、日期、元数据、发布前 MD、导出或质量门禁相关规则，都要同步检查两个项目的对应文档。若只更新其中一个项目，最终汇报必须说明另一个项目尚未同步及原因。

## 网站统一 Tag Pipeline

个人网页项目的分享、讲道、Custom Admin 和备用 Decap Admin 在新写入/新发布边界统一使用 Tag Pipeline。规则数据唯一来源为 `assets/admin/tag-rules.json`；Python 和浏览器运行时通过固定 fixture 做一致性验证。

- scripture 自动加入所有明确书卷；标题/副标题只按显式字典规则推断人物、地点、事件和主题。
- CLI `--tags` 与 Admin 人工输入继续保留，但都必须规范化别名、去重并通过 generic、歧义、字符和 2–6 Gate。
- `分享`、`灵命成长`、`讲道`、`教会讲道`、`文章`、`查经`、`生命反思`、`信仰`、`基督教` 一律拒绝。
- category、内容类型和 author/speaker 不自动生成标签；教会讲道不再写入旧式默认标签。
- 无足够精准规则结果时必须补充 `--tags`，不得 fallback。标签超过 6 个时也停止，不静默截断。
- 本规则只约束网站内部新写入；`website-publication-package/v1.2` 继续沿用既有兼容可选 tags 合同，v1.1 compatibility 也不改变；本 adoption 不触发历史文章或历史 package 迁移。

## 讲道 Owner 输入与网站发布消费

讲道翻译、Full Sermon Mode、E1、经文/ending fidelity、审核/修复轮次、Attempt 3 final repair 与 max-audit release semantics 由 `讲道整理` Owner 单独维护。网站 current authority 不再复制这些业务规则正文。当前 canonical reference：`../../讲道整理/docs/end-to-end-content-publishing-workflow.md §4.4.1/§4.4.2/§4.4.3`、`../../讲道整理/docs/translation-fidelity-quality-control.md`、`../../讲道整理/docs/sermon-independent-audit-orchestration.md`。

网站默认通过已登记的 `website-publication-package/v1.2` 消费讲道 Owner 已成立的正式中文稿/英文源 identity 与 SHA、publication-facing fidelity status/evidence、发布前 Markdown 和发布元数据；v1.1 继续用于历史、已生成、在途 package 与显式兼容。网站不得把自己的构建、正文一致性、SHA、JSON、display 或 import 结果解释成新的 sermon fidelity verdict。

网站侧仍负责并保持以下 Gate：

- publication package 的消费、identity/SHA/metadata/目标路径检查与 fail-closed；
- raw/processed/posts 的网站副本与 locked identity；
- Markdown 段落/标题/列表等显示结构；
- 正文经文的 TTS-friendly rendering，以及 frontmatter/SEO/scripture metadata 的网站机器格式；
- slug/articleId、description/tags、build、Git、deploy、SEO、notification 与线上验证。

以后讲道 Owner 规则变化时，只检查 canonical reference 与 current default `website-publication-package/v1.2`（以及需要时的 v1.1 compatibility）consumer/contract compatibility；不再在两个项目同步复制 sermon fidelity 规则正文。

## 已发布讲道正文修正与 GEO 标签补正

对已经发布的讲道执行逐篇重审时：

1. 只修改正文及必要的中文段落结构；原有 slug、标题、日期、articleId、作者、分类、经文和 source 必须保持不变。
2. 禁止调用邮件发送、补发、订阅通知、`workflow_dispatch` 或任何会触发读者提醒的流程。
3. 每篇都要以英文原稿逐段对照，并留下独立审计记录；自动风险评分只能用于排序，不能替代人工核对。
4. 修正后同步 raw、processed 和原 slug 对应 post 的正文，并验证正文一致。
5. frontmatter 仅允许补正 `tags`：通常 2-6 个，优先包含对应圣经书卷与文章核心主题；同一概念使用统一写法，不添加与正文无关的 SEO/GEO 关键词。
6. 未达到“无遗漏、无摘要化、无未确认缺口、中文自然可读、现场语境正确、标签准确”不得标记完成。

## 正文与日期质量门

生成 `data/processed/` 和 `src/content/posts/` 中的 Markdown 前，必须确认正文格式适合 Astro/Markdown 前台渲染：

- 段落之间必须有空行；单换行不会在公开页面形成独立段落。
- Admin 编辑区能看到换行，不代表前台会分段；以前台 Markdown 渲染结果为准。
- `[WD]`、`[SLIDE]`、`[slide]`、`[SLIDE - ...]`、`[TIMELINE SLIDE - ...]`、`[MAP]`、`[PAGE ...]` 等讲稿/投影片标记不得进入中文原稿、processed 或正式 posts。
- 若标记独占一行，删除整行；若标记后有正文，只删除标记，保留正文。
- 讲道内容的 `date` 一律使用本次整理发布时的日期；不得从原始文件名、讲道内容、历史讲道日期、文件修改时间或用户旧日期线索推断。补录旧讲道也按整理发布当天进入网站时间线。非讲道文章如用户明确指定发布日期，仍按对应内容流程处理。
- 从 `讲道整理` 项目导入的讲道，必须完成 raw/source 交接、processed 副本、posts 文件、NAS 归档状态记录；不能只复制 posts 文件后跳过 `archive-sermon`。NAS 归档内容只包含原始文件、英文原稿文件、翻译后的中文原稿文件，不归档发布前 MD、审计中间目录、网站 posts 或 processed 副本。

## 分享流程

0. 发布前同步远端：

   ```shell
   npm run sync
   ```

   这一步必须在任何文章修改、导出、构建、提交或推送之前执行。`npm run sync` 内部使用 `git pull --rebase origin main`，用于先把本地 `main` rebase 到远端最新状态，避免覆盖用户通过 Admin 后台、GitHub 网页或其他账号已经发布的内容。若本地已有未提交改动，必须先暂停并确认，不得跳过同步后继续发布。

1. 只读检查：

   ```shell
   python scripts/content_workflow.py inspect share
   ```

2. 将文件校验后移入 `data/raw/分享/`：

   ```shell
   python scripts/content_workflow.py ingest share
   ```

3. 预览整理正文并生成文章：

   ```shell
   python scripts/content_workflow.py publish share --source-file "data/raw/分享/<file>" --dry-run --description "人工概括型摘要。" --tags "核心人物,核心地点,核心主题"
   ```

4. 确认标题、经文、摘要和目标路径无误后正式发布：

   ```shell
   python scripts/content_workflow.py publish share --source-file "data/raw/分享/<file>" --description "人工概括型摘要。" --tags "核心人物,核心地点,核心主题"
   ```

5. 人工检查本次文章、整理报告和 Git 差异，然后执行构建、提交、推送和线上验证。

成功标准：收件目录不再保留已处理文件；原始文件 SHA-256 校验通过；只更新分享文章；线上页面包含正确标题、分类和正文。

## 讲道流程

0. 发布前同步远端：

   ```shell
   npm run sync
   ```

   这一步必须在任何讲道资料入库、文章生成、构建、提交或推送之前执行。`npm run sync` 内部使用 `git pull --rebase origin main`，用于先把本地 `main` rebase 到远端最新状态。若同步失败、发生 rebase 冲突，或本地已有未提交改动，必须暂停并与用户确认，不得继续发布。

1. 只读检查：

   ```shell
   python scripts/content_workflow.py inspect sermon
   ```

2. 确认日期、经文标题和讲员后入库：

   ```shell
   python scripts/content_workflow.py ingest sermon --date YYYYMMDD --title "经文与标题" --speaker "讲员"
   ```

3. 脚本把 PDF 移入 `data/raw/教会讲道/<日期标题_讲员>/`，进行 SHA-256 校验，并生成 `*.extracted.txt`。
4. Codex 检查提取质量，过滤页眉、页脚和异常字符，按“翻译原则”逐句完整翻译并校订为中文 TXT。机器提取稿不能直接发布，也不能把逐句翻译替换成概括式整理稿。
5. 将完成的讲道源资料复制到受保护归档区：

   ```shell
   python scripts/content_workflow.py archive-sermon --folder "data/raw/教会讲道/<日期标题_讲员>"
   ```

   归档脚本必须采用白名单逻辑，只复制三类文件：原始文件、`*.english-source.txt`、最终中文 `.txt`。不得归档 `metadata.json`、`*.json`、`*.csv`、`*.md`、`*.log`、`*.extracted.txt`、processed 副本、posts 文件、审计报告或其他可再生成资料。

   Mac 端执行前先确认归档区实际挂载，例如 `/Volumes/share/教会讲道`。如果未挂载或找不到目录，本轮不得假装归档完成，只能记录 `archive_status=pending`。归档目标目录已存在时必须停止，不得合并或覆盖。

6. 预览生成讲道文章和目录：

   ```shell
   python scripts/content_workflow.py publish sermon --folder "data/raw/教会讲道/<日期标题_讲员>" --dry-run --description "人工概括型摘要。"
   ```

7. 确认标题、讲员、经文、摘要、slug 和目标路径无误后正式发布：

   ```shell
   python scripts/content_workflow.py publish sermon --folder "data/raw/教会讲道/<日期标题_讲员>" --description "人工概括型摘要。"
   ```

   如需更新同一 source folder 对应的既有文章，必须显式加 `--update-existing`，且只能更新 registry 中记录的原 slug/path。

   若 scripture 与标题规则不足以生成至少 2 个精准标签，在 dry-run 中增加 `--tags "核心人物,核心地点,核心主题"`。不得以讲员姓名、`讲道` 或 `教会讲道` 补足数量。

8. 检查本次文章、讲员、经文、分类和 Git 差异，然后执行构建、提交、推送和线上验证。

成功标准：原始 PDF 和中文 TXT 均已保存；项目与归档副本的 SHA-256、文件数和字节数一致；只更新讲道文章；线上页面包含正确标题、讲员、分类和正文。

## 安全边界

- `data/raw/` 只新增，不直接改写原始文件。
- 受保护归档区默认只新增，不移动、不删除、不覆盖。唯一例外是：已经发布并归档的讲道因漏译或概括性翻译而重译，且用户针对当前重译任务明确授予临时覆盖权限时，可以只覆盖 `/Volumes/share/教会讲道/<对应目录>/` 中原有的最终中文 `.txt`。执行前必须确认真实挂载并唯一匹配目录；覆盖前后记录路径、大小与 SHA-256；PDF、英文原稿及其他文件仍禁止修改。未挂载时记录 `nas_overwrite_status=pending_mount`，匹配不唯一时记录 `blocked_ambiguous`，哈希不一致时记录 `failed_hash`。
- 任何目标已存在时，统一入口脚本都会停止，由用户或 Codex先核对，不自动覆盖。
- 分享发布必须指定 `--source-file`，讲道发布必须指定 `--folder`；不得无参数全量扫描 raw 目录。
- 正式发布前必须先运行 `--dry-run`，确认只会生成本次目标文章和报告。
- `description` 必须是人工概括型摘要，不允许正文截取、模板句或占位符。
- 讲道导入会维护 `docs/内容整理报告/sermon-import-registry.csv`，用于锁定 source folder、source SHA-256、slug、processed path 和 post path。
- 讲道经文若在 folder、文件名、正文前部之间冲突，脚本会停止，必须人工确认后再发布。
- raw 讲道目录名必须让脚本能解析完整经文范围。若 `马可福音7章24-30节` 被解析成 `马可福音 7`，可改用 `马可福音7:24-30` 这种明确格式；修改后必须重新 dry-run，确认 folder、文件名和正文经文一致。
- 导入脚本不会清空 `src/content/posts/`，也不会删除另一类别的文章。
- 发布前必须先执行 `npm run sync`，确认本地 `main` 已通过 `git pull --rebase origin main` 同步到远端最新状态；没有完成同步，不得开始修改、导出、构建、提交或推送。
- 发布前必须检查 `git diff`，发布后必须验证线上页面。
- push 后线上 URL 可能先返回旧站点页面或首页内容，即 HTTP 200 但不含新文章标题/经文/正文代表句。此时记录为 `published_online_pending_verify`，稍后重新验证；不要把“200 响应”单独当作线上验证完成。
- 发布前必须抽查正文段落空行和讲稿/投影片标记清理结果，尤其是讲道稿中的 `[WD]`、`[SLIDE]` 等来源标记。
- 讲道导入/导出脚本必须把 `date` 设为本次整理发布日；不得为了旧讲道而使用历史日期。非讲道文章的指定发布日期规则按对应内容流程处理。
- 讲道发布必须完成 NAS 归档或记录 `archive_status=pending/skipped_by_user`；未归档时不得在交接中写成完整完成。
